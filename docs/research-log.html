L Message（エルメ）予約管理 UX改善提案 ・ 井上友希 ・ 相談開始日 2026年10月24日

ChatGPT Workとのリサーチ段階の相談のうち、予約管理の改善に関する部分を時系列で要約しました。実際の相談ログには個人的なやりとりも含まれるため、該当部分は除いています。自分の発言は原文のまま、AIの回答は要点をまとめて掲載しています。

最初の依頼（2026年10月24日）

自分の依頼

あなたは、SaaSプロダクトのUXリサーチャー、プロダクトマネージャー、UI/UXデザイナー、競合分析の専門家です。（中略）あなたには、制作前の徹底した機能調査、競合比較、ユーザー課題の発掘、改善テーマの選定支援をお願いします。

依頼した内容（全16項目から抜粋）

  • L Messageの現行機能の網羅的な調査（公式サイト・マニュアルを最優先）
  • サロン・面談予約機能の重点調査
  • LiME、リピッテ ビューティー、RE:RE、リザービア、Lステップ、STORES 予約、Re:Startとの競合比較
  • 競合の機能を、LINE公式アカウントの拡張ツールとして実現できるかでA〜Eの5段階に分類
  • ユーザーの困りごとの発掘と、美容業界以外への応用可能性
  • 改善テーマ5〜8案と上位3案の比較、実機で検証するためのチェックリスト

守ってもらったルール（抜粋）

  • 公式情報で確認できた事実と、推測・仮説を分ける
  • 実装済みの機能を、新しい機能として提案しないことが重要です
  • コードで画面を再現できることと、実際にLINE・エルメへ実装できることは別である点に注意してください
  • この段階では、勝手に最終テーマを決定したり、プロトタイプ制作を始めたりしないでください

この依頼で決めていたこと

  • 調査と改善テーマの候補出しはAIに任せ、最終的なテーマは自分でエルメを操作してから決める
  • 事実と推測を分けさせ、確認できないことは「未確認」と書かせる
  • 競合の機能をそのまま持ち込まず、LINEの拡張ツールとして実現できる範囲で考える
  • 美容師としての現場経験を活かしつつ、ほかの業種にも役立つかを検討する

AIの回答（要約）

AIの回答

現行機能一覧、7社の競合比較、実現可能性の分類、改善案7つ、上位3案、実機検証のチェックリストをまとめた調査資料が届きました。上位3案は次のとおりです。

  • ① 長い予約枠を残す開始時刻の提案（AIの暫定推奨）：予約後に残る空き時間まで比較し、おすすめの時刻と理由を表示
  • ② 予約できない理由の診断：コース・日時・担当を指定すると、予約できない理由と修正箇所を説明
  • ③ 欠勤・変更の影響確認：影響を受ける予約、代わりの候補、お客様への確認と通知をまとめて扱う

あわせて、スマホでの予約管理や事前質問、予約前後の配信はすでにエルメに実装済みのため、そのまま提案すると既存機能との差分が弱くなる、という指摘もありました。

自分の判断

AIの推奨案はそのまま採用せず、実際にエルメで予約システムを構築してからテーマを決めました。

構築自体はとても簡単にできましたが、プレビューが画面単体ごとのため、予約の流れ全体が見えませんでした。そこで、いったん大枠だけを作ってLINE上に公開し、実機で流れを確認しながら細部を詰めていきました。

この体験から、空いている右側のスペースに、予約の流れ全体を確認できるリアルタイムプレビューを置く案（07）を考えました。事業者がお客様目線でプレビューを見ながら構築することで、「この項目を入れた方がわかりやすいかも」「ここでフォームを入れておこう」といった改善点に気づきやすくなります。範囲は予約システムのプレビューに限定し、実際の予約につながるバックエンドは含めず、フロントエンド内で収まる形にしています。

AIの反応（要約）

AIの回答

AIは、自分が先に挙げた仮説よりも、実際に構築して感じた不便さを起点にしているため、提案の理由が明確だと評価しました。そのうえで、次の点を整理してくれました。

  • 問題は「設定が難しい」ことではなく、「お客様の予約の進み方を確かめるには、LINEと管理画面を往復する必要がある」こと
  • 中心となる新仕様は、右側に置くことではなく、「設定と連動して、一連の予約体験を試せること」
  • 具体的な仕様案：メニュー選択から確認まで操作できる／編集内容が反映される／途中までの入力を保持する／「最初から試す」「この画面から試す」を選べる
  • 日時はサンプルデータ、完了画面は模擬表示にし、実予約・LINE通知・決済は発生させない

実現可能性の確認

自分の質問「単体プレビューだと、その画面がどのように表示されているかの確認になってしまうけど、横断プレビューであれば『体験』も兼ねられるよね。でも、この仕様は実現可能なのか？」

AIの回答

想定している範囲なら技術的に実現可能。ただし、採用課題のプロトタイプを作れることと、実際のエルメへ組み込めることは分けて考える必要がある。

  • メニュー → 担当 → 日時 → 質問 → 確認の画面遷移や入力チェックは、LINE APIにつながずフロントエンドだけで作れる。日時やお客様情報はテストデータ、予約完了は模擬の画面にする
  • 実際の製品では、本番の予約画面と表示・入力チェックの仕組みを共通化するのが望ましい（エルメの内部構造が対応できるかは未確認）
  • プレビュー中に設定を変えたときの動きも決めておくと、新仕様として具体的になる
  • PC上のプレビューで、LINE実機の表示や動作をすべて保証することはできない。目的は「構築中に予約体験を繰り返し確認でき、最後のLINE実機確認までの往復を減らすこと」と整理する

自分の返答「そうです。実機とまるまる同じものを写す事が目的ではなく、構築者がお客様が迷わない予約システムを構築するためですから。」

AIの回答

目的は「構築者が、お客様の予約体験を確かめながら設計できること」。体験してみることで、構築者自身が次のような点に気づき、その場で修正できる。

  • メニューの説明だけで選べるか
  • 次に何をすればよいか分かるか
  • 必要な質問が、適切なタイミングで出てくるか
  • 確定前に、予約内容を十分に確認できるか

提案の中心は「設定内容と連動した、予約フローの体験プレビュー」で、右側への配置は、体験と編集を行き来しやすくするための画面設計。

自分の質問「実際に実機で確認しながら進められればいいけど、私みたいに完全新規でアカウント立ち上げてるわけではなければ（友達がいるアカウントをエルメと繋げる）構築途中の実機テストって難しいですよね？」

AIの回答

既存の友だちがいると、「お客様への影響を確認しながらテストする」手間が加わり、新規アカウントより気軽に試しにくいという見方は妥当。ただし、友だちがいるだけで構築途中の画面が全員に表示されるわけではなく、エルメには特定の友だちに予約ページを表示しない設定や、テストユーザーへの送信機能もある。そのうえで、構築者は次の点を気にする必要がある。

  • 構築途中の予約ページへ、お客様がアクセスできないか
  • 編集した設定が、すでに公開している画面に影響しないか
  • テスト予約で、通知・タグ付け・リマインドなどが動かないか

そのため、この提案は「既存のお客様への公開や予約処理を伴わず、編集中の内容で予約体験を試せる」という価値も持つ。課題は「実機テストできない」と断定せず、「実機確認には公開範囲や自動処理への配慮が必要で、構築中に繰り返し試す負担がある」と整理するのが正確。

ほかの案の検討

自分の質問「他に良い案ありますか？」

AIの回答

今の横断プレビュー案を比較の基準にして、実際に触って感じた困りごとから探すのがよい。今の案に近いところでは、次の3つが考えられる（いずれも既存機能との差分は要確認）。

  • 公開前の確認・変更差分：編集前後を比較し、変更する内容を確認して公開する
  • 設定とお客様画面の対応表示：プレビュー内の項目を押すと、対応する編集欄が開く（横断プレビューと特に相性がよい）
  • 条件を変えて予約体験を試す：初回客・リピーターなどの架空の条件を切り替えて、表示の違いを確認する

ただし最初から全部盛りにせず、基本のプレビューで足りないものを見て追加するのがよい。美容室の課題をAIの想像で決めるより、「現場ではこう動くのに、この仕組みだと困る」という発見を一緒に仕様へ落とす方が強い。別案を探すなら、次は予約変更や日々の管理で引っかかるところを見ると比較しやすい。

テーマの決定

AIとの相談を踏まえ、実際にエルメを操作して感じた困りごとから、次の3つを提案の柱に決めました。

  1. 本日／新着の予約ページ：右へスクロールしないと詳細ボタンが出てこないため、お名前のクリックでモーダルが開くようにする（01）
  2. 予約詳細モーダル：予約履歴の左に同じ形でお客様カルテのボタンを置き、施術カルテを見られるようにする（02）
  3. 予約設定画面：画面右側にリアルタイムプレビューを付ける（07）

①②の理由：常連のお客様なら名前を見てすぐにわかりますが、来店回数が少ないお客様はカルテを見ないと思い出せません。予約が入ったときに、すぐカルテを確認できるようにしたいと考えました。その途中でスクロールの手間があったため、お名前のクリックでモーダルが開くようにしました。

③の理由：個人サロン、特にひとりで営業しているサロンほど、システムの導入費用や構築費が障壁になります。自分で構築できるのはエルメの強みですが、構築するのはプロだけでなく個人事業者でもあります。私自身、構築中は全体像が見えず、LINEでいったんテストして前後の流れや遷移のタイミングを見たときに、はじめて「このテキストを入れよう」「このフォームがあった方がわかりやすいかも」と気づきました。

AIによる整理

AIの回答

3点は「予約システムを自分で構築し、日々の接客に活用するまでの改善」としてまとめられる。そのうえで、各提案の価値を次のように整理してくれました。

  • ①改善するのはスクロール量ではなく、「予約者を見て、前回どんな施術をした方か思い出すまでの手間」。現状は「名前を確認 → 横スクロール → 詳細 → 必要な顧客情報を探す」、改善後は「名前をクリック → 予約詳細 → カルテを確認」
  • ②お客様情報（氏名・連絡先などの基本情報）と、施術カルテ（来店ごとの施術内容や申し送り）を区別し、来店単位の記録を積み重ねて予約からすぐ参照できることが新仕様の中心
  • ③構築者がお客様として予約を進めながら、説明不足や質問のタイミングに気づいて編集できることを主な価値にする。費用面の効果は、自力での構築を支えた結果として検証する位置づけ
  • ターゲットや事業面の見込みなどは現段階では仮説のため断定せず、自分の経験として説明する方が正確

自分の補足「詳細ボタン押せばその人のモーダルがでます」

AIの回答

「詳細」で開く既存のモーダルを、一覧のお客様の名前からも開けるようにする。そのモーダル内の「予約履歴」の左に「お客様カルテ」ボタンを追加する。①は既存モーダルへのアクセス改善、②はそこから参照できる施術カルテの新設で、モーダル自体を新しく提案するわけではない。

自分の指摘「『現状：名前を確認→横スクロール→詳細→必要な顧客情報を探す』っていってたけど、必要な顧客情報ではなく、現状該当の顧客情報がでますってこと。」

AIの回答

AIは「必要な顧客情報を探す」は誤りだったと認め、次のように訂正しました。

  • 現状：名前を確認 → 横スクロール → 「詳細」→ 該当のお客様の情報がモーダルに表示される
  • 改善後：名前をクリック → 同じモーダルが表示される

①の改善は、横スクロールせずに該当のお客様の情報を開けること。カルテの新設は②の別の提案。
